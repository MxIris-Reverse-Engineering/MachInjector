# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

It deliberately does **not** restate what `Documentations/` already covers. A project-level guidance
file was removed once before (`e558c42`) precisely because it had drifted out of sync with the
design documents. Keep this file to things an agent needs that are *not* derivable from the code or
the docs — build steps, hazards, and pointers. When in doubt, add the material to `Documentations/`
and link it from here.

## Project Overview

Objective-C library for injecting a dylib into another process on macOS. Three distinct injection
paths, not three variations of one:

| Class | Mechanism | Architectures |
|---|---|---|
| `MIMachInjector` | shellcode in the target calls `dlopen`; synchronous | arm64, arm64e, x86_64 |
| `MIMachInjectorAsync` | same, but completion is event-driven (`MACH_SEND_DEAD`) | arm64, arm64e |
| `MIMachInjectorRemap` | **never calls `dlopen`** — maps the payload's segments in and replays dyld's work by hand | arm64, arm64e only |

- **Library target**: `MachInjector` (SPM library product, source distribution)
- **Swift tools version**: 5.9 — **`swift-testing` is unavailable**, tests use XCTest
- **Platform**: macOS 10.15+
- **Dependencies**: none

**Start here for how any of it works**:
[`Documentations/Design/InjectionStrategies.md`](Documentations/Design/InjectionStrategies.md).

## Build & Test

Always use a private scratch path so the agent does not fight the user's own build:

```bash
swift build --scratch-path /tmp/claude/SwiftPM/MachInjector 2>&1 | xcsift
swift test  --scratch-path /tmp/claude/SwiftPM/MachInjector
```

Run a single test:
```bash
swift test --scratch-path /tmp/claude/SwiftPM/MachInjector --filter MIMachInjectorRemapRestoreTests
```

**Judge test success by the raw exit code, never by xcsift's summary.** For builds, xcsift's
diagnostics are accurate and worth using; for tests they are not trustworthy in general. Tests here
are XCTest, which xcsift does parse correctly — but do not rely on that holding if a `swift-testing`
target is ever added.

```bash
swift test --scratch-path /tmp/claude/SwiftPM/MachInjector > /tmp/out.txt 2>&1; echo "exit=$?"
```

### Regenerating the remap loader — manual, and easy to forget

The remap path embeds a separately-compiled fat dylib as a C byte array. It is **not** built by SPM.
After changing any of `loader_arm64_remap.s`, `loader_arm64_remap_fixup.c`, or
`loader_arm64_remap_handoff.c`:

```bash
./Loader/build_loader.sh   # recompiles, ad-hoc signs, rewrites loader_arm64_remap_dylib.h
touch Sources/MachInjector/MIMachInjectorRemap.m
```

The `touch` is not optional: build systems do not track the generated `.h`, so the `.m` will not be
recompiled and the *old* loader bytes stay embedded. This has burned people before — a target kept
crashing because the header had been regenerated but the `.m` had not.

`build_loader.sh` disassembles `_remap_stage1_entry` and fails the build if `paciza` is missing,
guarding a regression where the pthread start routine was handed over unsigned.

## Repository Layout

```
Sources/MachInjector/
  MIMachInjector.m              sync dlopen path
  MIMachInjectorAsync.m         async dlopen path
  MIMachInjectorRemap.m         remap path (the 13-step recipe)
  MIMachInjectorRemapRestore.c  step 7c — restore writable segments from the file
  MIMachInjectorInternal.h      internal header, NOT in include/ (see below)
  MIMachInjectorRemapInternal.h internal header, NOT in include/ (see below)
  loader_arm64.s                sync shellcode (arm64/arm64e)
  loader_x86_64.s               sync shellcode (x86_64)
  loader_arm64_async.s          async shellcode
  loader_arm64_remap_dylib.h    GENERATED byte array; never edit by hand
  include/                      public headers (this is the API surface)
Loader/                         remap loader sources — outside the SPM target on purpose
  build_loader.sh               regenerates the byte array above; run by hand
  loader_arm64_remap.s          stage-1 shim
  loader_arm64_remap_fixup.c    apply_fixups
  loader_arm64_remap_handoff.c  pthread_thunk + perform_runtime_handoff
Tests/MachInjectorTests/        XCTest; compiles its dylib fixture at runtime via clang
Documentations/                 see Documentations/README.md
```

The two `*Internal.h` headers sit beside the implementation rather than in `include/` so they stay
out of the public module. The test target reaches them through a `headerSearchPath` in
`Package.swift`. Do not move either into `include/` to make something compile — that would turn it
into API. Both exist for the same reason: the interesting decision is separated from the
cross-process act that needs root, so the decision can be unit-tested. `MIMachInjectorInternal.h`
holds the dlopen report layout and the verdict function; `MIMachInjectorRemapInternal.h` holds the
segment layout and the writable-segment restore.

`Loader/` sits outside `Sources/` so SwiftPM never compiles it. Those three files are built only by
`build_loader.sh`, into a standalone dylib; the library consumes them purely as the generated byte
array, and `MIMachInjectorRemap.m` resolves every loader symbol through `dlsym` on the dlopened copy
— it never references one statically. They lived under `Sources/MachInjector/` until 2026-08-11,
where SwiftPM *did* compile them, linking a second and entirely unused copy of `_apply_fixups`,
`_remap_stage1_entry`, `_pthread_thunk` and the `_cfg_*` slots into every downstream binary. Do not
move them back.

## Hazards

Things that have actually gone wrong here, in rough order of how much time they cost:

- **A crash that looks like a PAC bug usually is not one.** If a remapped payload dies on a pointer
  whose value is legitimate but whose authentication bits are wrong, read
  [`Documentations/Internal/InjectorRuntimeDirtyState.md`](Documentations/Internal/InjectorRuntimeDirtyState.md)
  before touching any signing code. The signing has been verified slot-by-slot against `dyld_info`.
- **The injector's `dlopen` of the payload dirties its `__DATA`.** Anything written at load time by
  the Swift/ObjC runtimes is process-private and is not covered by chained fixups. Step 7c exists to
  undo that; do not remove it.
- **Raw mach threads have no TLS.** They cannot `ret`, cannot call anything MIG-backed (including
  `thread_terminate` on themselves), and crash at address `0x10` when they try. See
  [`Documentations/Design/DlopenInjectionInternals.md`](Documentations/Design/DlopenInjectionInternals.md).
- **Never `dlclose` a handle whose image was remapped into a target.** dyld's unload path
  `mprotect`s those pages and the change propagates through the shared VM object, killing the target
  with `KERN_PROTECTION_FAILURE`. The three handles are leaked on purpose.
- **`csops(CS_OPS_STATUS)` reporting `CS_REQUIRE_LV` does not predict a `dlopen` refusal.** Attempt
  the injection and branch on the result. Rationale is in the `MIMachInjector.h` docblock.
- **Disabling SIP does not disable library validation.** It only lets `amfid` read
  `/Library/Preferences/com.apple.security.libraryvalidation.plist`; the actual switch is that
  file's `DisableLibraryValidation` key. Necessary, not sufficient — so a fresh SIP-disabled
  machine still rejects a non-platform payload going into a platform binary
  (`mapping process is a platform binary, but mapped file is not`), and setting the key while SIP
  is on does nothing at all. This one gets rediscovered roughly every time someone sets up a new
  machine; see
  [`Documentations/Design/InjectionStrategies.md`](Documentations/Design/InjectionStrategies.md).
- **The two result-code encodings are not the same.** `MIMachInjectorDlopenResultCode` (sync) and
  the async notepad's `result_code` assign opposite meanings to `1`. Both declarations carry a
  cross-referencing warning; read it before touching either. Neither of them is an
  `MIMachInjectorErrorCode`: those two are the injector's private protocol with its own shellcode,
  the error codes are API, and no value should ever be carried from one into the other.
- **The three error-code enumerations do not share one numbering.** The two dlopen paths agree with
  each other on purpose — `3` is a missing task port in both — precisely so a caller can share a
  `switch`; that is why the synchronous path's values have holes in them, and the holes must stay.
  The remap path does not agree with them (`10` is its task-port failure) because its numbering was
  published first and renumbering would break the one contract that existed. New failure points are
  appended past the highest value in the paths that share a numbering; nothing is ever renumbered.
  Proposal 0002 has the reasoning.

## Conventions

- **Substantive changes go through a proposal first.** New features, architecture changes, breaking
  API changes, large refactors: write `Documentations/Evolutions/NNNN-*.md` and get it approved
  (status `Accepted`) before writing implementation code. Obvious bug fixes and typos are exempt.
  Proposal status updates land in the same commit as the implementation.
- **Docs are part of the change, not a follow-up.** Every batch must explicitly decide whether
  documentation needs updating, and say so even when the answer is no. New or renamed documents must
  be registered in `Documentations/README.md`.
- **Fixes ship with a reproducing test that was verified to fail first.** Keep it as a regression
  test. The cross-process parts cannot be unit-tested without root, so isolate the byte-level
  decisions from the VM writes and test the former — `MIMachInjectorRemapRestore.c` is the pattern.
- **Public API changes are source-compatibility events.** This is a source-distributed SPM library
  with no ABI constraint, but downstream repos recompile against it. Additive changes are safe;
  anything else needs to be called out in the proposal.
- **No abbreviations in identifiers**, including generic parameters. Match the surrounding code's
  comment density and idiom.
- **Error enums, domains and userInfo keys get a dotted `NS_SWIFT_NAME`.** `MachInjector.Error`,
  `MachInjector.errorDomain`, `MachInjector.remoteErrorMessageKey` — the shape Apple publishes
  `BGTaskScheduler.Error` in. On an `NS_ERROR_ENUM` the dotted form is load-bearing, not cosmetic:
  a flat name renames only the enumeration and leaves the error type Swift synthesizes under its
  ObjC-derived name, giving one type two Swift names. Apple spells this in `.apinotes` instead,
  which is not available to us — apinotes are read by the consumer's ClangImporter, so every
  downstream target would have to pass `-Xcc -iapinotes-modules` (verified; placing the file in
  `include/` does nothing).
- Comments and identifiers in English; internal design documents in Chinese.
